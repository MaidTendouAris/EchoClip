# 长时间录音卡顿修复（2026-09-15）

用户视频为 Windows 桌面，缓存接近 9 小时。录音期间界面卡顿，并出现音频采集错误。

## 原因与修改

共享 Rust 核心每收到一个音频块，都会在 `update_worker_status` 中遍历全部 PCM 文件、逐个查询文件大小。此时持有状态互斥锁；Windows 的同步 FFI 状态查询、Android 的录音状态读取和采集队列错误统计也会等待此锁。默认每分钟一个分片，9 小时即约 540 次磁盘元数据访问/音频块。写入队列积压后会拒绝新的音频块。

- `SegmentedRecorder` 改为增量维护保留的 PCM 字节数，成功写入时增加、过期分片删除时减少；恢复缓存时按实际文件长度重新校准一次。统计包含尚在写入缓冲中的 PCM 和导出锁定的分片，表示保留音频的逻辑大小，不含 JSON 清单或文件系统分配开销。
- 无完整分片过期时，清理与导出锁定文件集合的检查直接返回；不再为每个音频块分配并搬移整个分片列表。
- 分片删除失败时保留未删除文件的清单，之后可重试，避免提前退出 `drain` 导致清单丢失。
- 队列计数在消息交给工作线程前增加；入队失败时回滚，避免工作线程先取出音频块导致无符号计数下溢。
- 状态互斥锁内仅更新内存字段。未改变录音采样率、音频内容、缓存时长、导出格式或界面刷新频率。

## 可重复性能复现

```powershell
cargo run --release -p echoclip_core --example long_recording_probe
```

工具创建独立临时目录，生成 1、540、1440 个一分钟分片，再以 10ms 间隔提交 400 个音频块，同时每 50ms 查询状态。为缩小测试文件，PCM 采样率缩放为 100Hz；保留真实分片数量和回调频率。检查实际写入样本数与成功提交数一致，结束后只删除自己创建的临时目录。

同机 Windows、Release 构建的一轮结果如下。时间受机器负载影响；这是受控缓存规模复现，不是已经连续录制 24 小时的实机测量。

| 缓存规模 | 修复前查询 P95 / 最长 | 修复后查询 P95 / 最长 | 修复前拒绝音频块 | 修复后拒绝音频块 |
| --- | --- | --- | --- | --- |
| 1 个分片 | 0.007 / 0.035 ms | 0.007 / 0.190 ms | 0 / 400 | 0 / 400 |
| 9 小时 / 540 分片 | 365.933 / 464.933 ms | 0.005 / 0.008 ms | 235 / 400 | 0 / 400 |
| 24 小时 / 1440 分片 | 467.626 / 741.025 ms | 0.005 / 0.012 ms | 318 / 400 | 0 / 400 |
